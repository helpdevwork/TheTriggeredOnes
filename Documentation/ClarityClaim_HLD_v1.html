Section 02

Architecture Principles

These five decisions govern every component design choice in this document. Any team member building a component should check their approach against these before writing a line of code.

P1 — Local-First

Everything runs on the GPU machine

No model inference call leaves the local network. LM Studio serves all models at localhost:1234. ChromaDB runs at localhost:8001. The backend runs at localhost:8000. The frontend at localhost:5173. The demo must work with the ethernet cable physically unplugged. This is non-negotiable — it is the single biggest differentiator from every competing team.

P2 — One Data Object

A single JSON object flows through all stages

The ClinicalRecord object is created in Stage 1 and enriched at every subsequent stage. No data is re-entered. No redundant API calls. The FHIR patient record, the transcript, the SOAP note, the ICD codes, and the validation scorecard all live inside one object that the frontend renders progressively as each stage completes.

P3 — Right Model, Right Task

Each model is assigned exactly one job

Qwen3.6-35B Instance 1 owns documentation generation. Instance 2 owns validation. Gemma4-26B owns second-pass compliance. Llama3.2-1B owns patient summaries. Phi3.1-mini owns fast classification. Nomic owns embeddings. No model is used outside its assignment. Phi-2 is excluded entirely. This prevents GPU memory contention and keeps inference times predictable.

P4 — Fail Gracefully in Demo

Every live call has a static fallback

Before the hackathon presentation, pre-generate the SOAP note, validation result, and patient summary for the demo scenario and save as JSON files. If any live inference call takes too long or errors during the demo, the frontend silently serves the pre-generated fallback. Judges see a seamless demo. This is architectural insurance, not cheating.

P5 — Build for Demo, Not Production

Complexity stops at demo requirements

No authentication, no database persistence, no multi-user sessions, no deployment infrastructure. The backend is stateless per request. ChromaDB is file-persisted on disk. Everything is localhost. The 48-hour clock is real — every hour spent on production features is an hour stolen from demo polish. YAGNI applies hard here.

Component 01

Whisper — Local Speech-to-Text

Whisper converts the clinical encounter audio into a text transcript that Stage 1 (Qwen documentation) processes. It runs entirely on-device, processes pre-recorded files, and outputs plain text.

What it does

Input
Audio file (.mp3 / .wav / .m4a)
Received from the frontend recorder or uploaded directly. Backend saves to /tmp/encounter.wav.
Process
Local Whisper inference
Python calls whisper.transcribe("encounter.wav", language="en"). Uses medium model (~1.5GB). No GPU contention with LLMs — runs on CPU or separate VRAM allocation. Takes 15–45 seconds for a 60-second clip.
Output
Plain text transcript + timestamps
Whisper returns a dict with text (full transcript) and segments (timestamped sentences). The backend streams segments to the frontend via SSE for the real-time effect, then sends the full text to Qwen.

Configuration

Model Selection

Use medium for the hackathon. Large-v3 is more accurate but slower. Medium handles clinical terminology reliably. Do not use tiny or base — they misrecognize medical terms like "radiculopathy", "metformin", "HbA1c".

Demo Safety

For the live demo, use a pre-recorded 45-second audio clip rather than live microphone recording. This eliminates background noise, ensures consistent timing, and removes the STT failure as a live risk point. The pre-recorded clip is played through the UI's audio recorder control.

Offline Capable

Whisper is fully local after install. No internet connection needed. The model weights are downloaded once at install time and cached locally.

Python Integration (Backend)

# whisper_service.py import whisper import json model = whisper.load_model("medium") # load once at startup def transcribe_audio(audio_path: str) -> dict: result = model.transcribe(audio_path, language="en") return { "full_text": result["text"], "segments": result["segments"], # [{start, end, text}, ...] "language": result["language"] }

# /api/validate — the most important endpoint async def validate_soap(soap_note: str, icd10_codes: list) -> dict: # Step 1: Retrieve relevant NCD/LCD policy chunks via RAG query = f"{' '.join(icd10_codes)} medical necessity documentation" policy_chunks = chromadb_retrieve(query, top_k=3) # Step 2: Qwen Instance 2 — primary gap analysis (240K ctx) qwen_prompt = build_validation_prompt(soap_note, policy_chunks) qwen_result = await call_model(QWEN_INSTANCE_2, qwen_prompt) qwen_parsed = parse_json_response(qwen_result) # returns: { gaps: [...], approval_score: 0-100, fixes: [...] } # Step 3: Gemma — independent second-pass compliance check gemma_prompt = build_compliance_check_prompt(soap_note, policy_chunks) gemma_result = await call_model(GEMMA, gemma_prompt) gemma_parsed = parse_json_response(gemma_result) # Step 4: Merge scores (Qwen weighted 0.6, Gemma 0.4) final_score = round( qwen_parsed["approval_score"] * 0.6 + gemma_parsed["approval_score"] * 0.4 ) # Step 5: Flag disagreements for human review disagreements = find_disagreements(qwen_parsed, gemma_parsed) return { "approval_probability": final_score, "gaps": qwen_parsed["gaps"], "fixes": qwen_parsed["fixes"], "policy_references": [c["source"] for c in policy_chunks], "human_review_flags": disagreements }
Component 03

RAG Pipeline — NCD/LCD Policy Retrieval

The RAG pipeline is what makes PS 39 technically credible. Instead of asking the LLM to reason from general knowledge, you retrieve the exact CMS policy document relevant to the patient's procedure codes and inject it into the prompt.

Indexing Pipeline — runs once before demo

Step 1
Read NCD/LCD PDFs
Use pypdf to extract text from each policy PDF downloaded from CMS. Clean whitespace and page headers.
Step 2
Chunk at 1500 tokens
Split each document into overlapping 1500-token chunks with 200-token overlap. This keeps semantic context across chunk boundaries. Use tiktoken to count tokens accurately.
Step 3
Embed via Nomic
Call Nomic Embed Text v1.5 via LM Studio for each chunk. Returns a 768-dim vector. Maximum 2K tokens per call — chunks must stay under this limit.
Step 4
Store in ChromaDB
Persist each chunk with its embedding, source PDF name, LCD ID, and page number as metadata. Collection name: ncd_lcd_policies. Total storage for 5 PDFs: approximately 80–120 chunks.

Retrieval — runs at every /api/validate call

import chromadb client = chromadb.PersistentClient(path="/data/chromadb") collection = client.get_collection("ncd_lcd_policies") def chromadb_retrieve(query: str, top_k: int = 3) -> list: # Embed the query using Nomic via LM Studio q_embedding = embed_text(query) results = collection.query( query_embeddings=[q_embedding], n_results=top_k, include=["documents", "metadatas"] ) return [ { "text": results["documents"][0][i], "source": results["metadatas"][0][i]["lcd_id"], "page": results["metadatas"][0][i]["page"] } for i in range(top_k) ]

Chunk size matters: Nomic Embed has a hard 2048-token limit. Set chunk size to 1500 tokens maximum. Going over silently truncates the embedding and degrades retrieval quality. Use tiktoken (not character count) to measure accurately.

Component 04

Model Layer — Prompt Engineering

The quality of the output depends entirely on how well the prompts are written. These are the exact prompt structures for each model call. Treat them as contracts — the output format must be JSON so the backend can parse it reliably.

SOAP Note Generation Prompt (Qwen Instance 1 — PS 37)

System: You are a clinical documentation specialist. You generate structured SOAP notes from doctor-patient encounter transcripts. You always output valid JSON. Use ICD-10 codes at the highest specificity level. Never use unspecified codes (e.g. prefer M51.16 over M54.5). Always link diagnosis codes to documented clinical evidence in the transcript. User: PATIENT CONTEXT (from FHIR record): {patient_context_json} ENCOUNTER TRANSCRIPT: {full_transcript} Generate a structured SOAP note. Return ONLY this JSON, no other text: { "subjective": "patient's reported symptoms in detail", "objective": "examination findings, vitals, lab results", "assessment": "clinical assessment with primary and secondary diagnoses", "plan": "treatment plan, referrals, follow-up", "icd10_codes": [{"code": "M51.16", "description": "...", "confidence": 0.94}], "cpt_codes": [{"code": "99213", "description": "...", "confidence": 0.88}], "clinical_reasoning": "brief explanation of key diagnostic decisions" }

NCD/LCD Validation Prompt (Qwen Instance 2 — PS 39)

System: You are a medical billing compliance specialist. You evaluate clinical documentation against CMS NCD/LCD coverage criteria. You identify exactly what is missing, insufficient, or inconsistent with payer requirements. Output valid JSON only. User: SOAP NOTE TO VALIDATE: {soap_note} RELEVANT NCD/LCD POLICY EXCERPTS: Policy 1 — {policy_source_1}: {policy_text_1} Policy 2 — {policy_source_2}: {policy_text_2} Policy 3 — {policy_source_3}: {policy_text_3} Evaluate this documentation against these policies. Return ONLY this JSON: { "approval_score": 74, "gaps": [ { "policy_ref": "LCD L35062", "requirement": "minimum 6 weeks conservative treatment documented", "current_doc": "documentation mentions back pain but no treatment duration", "severity": "critical" } ], "fixes": [ { "gap_ref": 0, "suggested_language": "Patient has undergone 7 weeks of physical therapy..." } ], "passing_criteria": ["diagnosis code M51.16 matches LCD criteria", "..."] }

Patient Summary Prompt (Llama 1B)

System: You explain medical information in simple, friendly language that patients can understand. Avoid medical jargon. Be warm and reassuring. Output plain text, no JSON needed. User: Based on this clinical note, write a short patient-friendly summary (3-4 sentences) explaining what happened at today's appointment, what the diagnosis means in simple terms, and what to do next. Language: {language} SOAP NOTE: {soap_note}
Component 05 — PS 31

FHIR Integration via HAPI Test Server

This is how PS 31 is solved without building a full interoperability platform. One real FHIR R4 API call at demo startup — then served from local cache for the rest of the demo.

HAPI FHIR — What to call

Call 1
GET /Patient/{id}
Returns demographics — name, DOB, gender, address. Use a patient with relevant conditions pre-existing in the HAPI test dataset.
Call 2
GET /Condition?patient={id}
Returns existing diagnoses as ICD-10 coded conditions. Shows the patient's medical history — fed directly into Qwen's SOAP generation prompt as context.
Call 3
GET /MedicationRequest?patient={id}
Returns current prescriptions. Qwen uses this to avoid drug interactions in the treatment plan and to reference relevant medication history.
Call 4
GET /AllergyIntolerance?patient={id}
Returns documented allergies. Critical for the documentation AI to include in the SOAP note Assessment/Plan.

Caching Strategy (for offline demo)

# fhir_service.py import httpx, json, os HAPI_BASE = "https://hapi.fhir.org/baseR4" CACHE_PATH = "/data/fhir_patient_cache.json" PATIENT_ID = "592" # confirm a valid ID before hackathon async def get_patient_context(patient_id: str) -> dict: # Serve from cache if available (offline safe) if os.path.exists(CACHE_PATH): with open(CACHE_PATH) as f: return json.load(f) # Otherwise fetch live and cache async with httpx.AsyncClient() as client: patient = (await client.get(f"{HAPI_BASE}/Patient/{patient_id}")).json() conditions = (await client.get(f"{HAPI_BASE}/Condition?patient={patient_id}")).json() meds = (await client.get(f"{HAPI_BASE}/MedicationRequest?patient={patient_id}")).json() allergies = (await client.get(f"{HAPI_BASE}/AllergyIntolerance?patient={patient_id}")).json() result = parse_fhir_bundle(patient, conditions, meds, allergies) with open(CACHE_PATH, "w") as f: json.dump(result, f) return result

Demo line: "Before the AI writes a single word, it pulls the patient's complete longitudinal record via FHIR R4 — the same standard that Epic and Cerner expose in production hospitals."

Component 06

React Frontend — 3 Screens

Vite + React + Tailwind. The frontend is a single-page app with three sequential screens. The same ClinicalRecord state object is progressively enriched as the user moves through each stage.

Shared State Object — ClinicalRecord

// types.ts — shared across all 3 screens interface ClinicalRecord { patient: FHIRPatientContext; // populated on Screen 1 load transcript: string; // populated after Whisper STT soap_note: SOAPNote; // populated after Screen 1 → 2 icd10_codes: ICD10Code[]; // part of soap_note cpt_codes: CPTCode[]; // part of soap_note validation: ValidationResult; // populated after Screen 2 → 3 patient_summary: string; // populated on Screen 3 }
Screen 1 — Encounter Capture

What the user sees

Left sidebar: FHIR patient card (auto-loaded on mount). Main area: audio recorder with waveform + real-time transcript streaming via SSE. Bottom: "Generate Clinical Note" button — disabled until transcript is populated.

Key interactions: Record audio → Whisper processes → segments stream in → user reviews transcript → click Generate → Qwen Instance 1 runs → navigate to Screen 2.

Screen 2 — SOAP Note Editor

What the user sees

Four editable text panels: S / O / A / P. Each panel is pre-filled by Qwen's output. ICD-10 code chips below the Assessment panel — each chip shows code + description + confidence %. CPT code chips similarly.

Key interactions: Edit any panel text → ICD code chips are clickable to remove/add → "Run Validation" button triggers PS 39 pipeline → navigate to Screen 3.

Screen 3 — Validation Scorecard

What the user sees

Top: animated approval probability gauge (0–100%). Middle: gap checklist — each row shows the policy requirement, what's missing, severity badge, and a "Fix This" button. Bottom: policy citation, patient summary panel.

Key interactions: Click "Fix This" → AI-suggested language appears → user clicks "Apply" → gauge re-animates upward → Regulatory Updates panel shows PS 35 layer.
