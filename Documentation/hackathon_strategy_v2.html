What the AI Does — PS 39

📖
Policy Retrieval

Given the ICD-10 + CPT codes from PS 37, the system retrieves the relevant NCD/LCD coverage policies via semantic search over the embedded CMS policy corpus.

🔍
Gap Analysis

AI compares the generated SOAP note against policy requirements. Identifies exactly which documentation elements are missing, insufficient, or contradict the coverage criteria.

✅
Pre-Submission Scorecard

Produces an approval probability score, a line-by-line checklist of required vs. documented elements, and specific language suggestions to close each documentation gap before submission.

Model Assignment for PS 39

qwen/qwen3.6-35b-a3b (Instance 2, 240K context) — Used here because the full NCD/LCD policy document (often 15–40 pages) plus the SOAP note must fit in context together. The model reasons about whether specific documentation phrases satisfy specific policy criteria — requires strong logical reasoning. google/gemma-4-26b-a4b-qat acts as an independent second-pass validator: it reads the same documentation and policy excerpt and returns a compliance judgment. Two models disagreeing triggers a human review flag — a safety mechanism judges will appreciate.

RAG Architecture (Critical for PS 39): The 11,000+ CMS NCD/LCD documents cannot all fit in context. Use text-embedding-nomic-embed-text-v1.5 to embed all policy PDFs into ChromaDB. At validation time, retrieve the top-3 most relevant policy chunks for the given procedure code. This is what separates your solution from a team that just prompts the LLM with general knowledge about insurance — you cite the exact policy document with the exact section number.

Problem Statement 35 — Background Layer

AI-Powered Regulatory Intelligence Agent

Repositioned as Internal Service

The Exact Problem

Business Analysts, Product Teams, and Project Teams currently rely on clients to communicate US healthcare regulatory and compliance changes. This reactive approach leads to delayed awareness, limited time for impact assessment and implementation, increased development pressure, and higher compliance risk. The opportunity: build an AI-Powered Regulatory Intelligence Agent that proactively monitors healthcare regulatory sources and delivers actionable compliance insights.

Why we don't demo this standalone: The problem is real and the AI solution is elegant, but a regulatory monitoring agent is a background process — there is nothing visually compelling to show a judge in 8 minutes. "Our AI reads government websites and sends Slack messages" doesn't generate the live wow-moment that wins hackathons. Instead, this becomes the technical depth answer during Q&A: "How does your NCD/LCD database stay current?" — "We built a regulatory intelligence scheduler that crawls the CMS website nightly, detects new coverage determinations using our Qwen model, and auto-updates our vector store." That's a sophisticated architecture answer that separates you from teams with static knowledge bases.

How PS 35 Powers the Product (Under the Hood)

Nightly Scheduler

A Python cron job checks the CMS Coverage Database, Federal Register, and OIG Compliance Alerts for new or updated policies. When changes are detected, the AI summarizes the regulatory impact and re-embeds updated policy chunks into ChromaDB.

Impact Assessment

For each new NCD/LCD, qwen3.6-35b generates a structured impact brief: which procedures are affected, which current claims may be at risk, and what documentation changes are required. This is exactly the "actionable compliance insight" PS 35 asks for.

Problem Statement 31 — Data Backbone

AI-Powered FHIR Interoperability Platform

Supporting Architecture Component

The Exact Problem

Healthcare data is fragmented across hospitals, payers, labs, and pharmacies. The opportunity: build an AI-powered FHIR-based interoperability platform that consolidates patient information into a single longitudinal record.

Why standalone PS 31 is a 2-year project, not a 48-hour hackathon: A true FHIR interoperability platform requires actual integration contracts with Epic/Cerner, live payer APIs, pharmacy system connectors, and real patient data pipelines. No team can demo this credibly in 48 hours. However — your demo can use the HAPI FHIR public test server (publicly available, free) to simulate FHIR R4 patient resource queries. You make a real FHIR API call, retrieve a synthetic patient record, and feed it into your PS 37 documentation AI. That's a real FHIR integration that takes 3 hours to build, not 2 years.

Step 1
Demo opens with: "Before the AI writes a single word, it pulls the patient's complete history." Make a live GET /Patient/[id] call to the HAPI FHIR test server. Show the JSON response — allergies, past diagnoses, current medications — populating the patient sidebar in the UI.
Step 2
This patient context is injected into the PS 37 documentation prompt. The AI knows the patient is diabetic, on metformin, with a prior hospitalization for DKA — it writes documentation that reflects this history, not just today's chief complaint.
Result
You've now touched PS 31 in your architecture. When a judge asks "how does your system get patient data?" — "We query FHIR R4 endpoints. In production, this would connect to the hospital's Epic or Cerner FHIR API. In this demo, we're using the public HAPI test server."

⚠️ Do not use phi-2 (TheBloke Q2_K): This is a 2-bit quantized model with a 2,048-token context window — shorter than a single clinical encounter transcript. It will silently truncate inputs and produce clinically incorrect outputs. The Q2_K quantization at this model size significantly degrades reasoning quality. Exclude it from all healthcare inference tasks. It is not listed above for this reason.

Resource Allocation Strategy for Live Demo

Pre-warm Both Qwen Instances

Send a dummy 100-token prompt to both Qwen instances 5 minutes before the demo. A cold start on a 22GB GGUF model takes 30–90 seconds of silence in front of judges. Pre-warming loads all weights into GPU VRAM so generation starts in <2 seconds.

ChromaDB Pre-indexed

Embed your 3–5 sample NCD/LCD PDFs into ChromaDB before the demo begins. The Nomic embedding model at 84MB runs in milliseconds. Index at startup. Retrieval at query time is <50ms for the top-k search — imperceptible to the judge.
